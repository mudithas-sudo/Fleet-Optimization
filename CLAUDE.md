# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

FleetOps — a demo prototype showcasing Google ADK + Google Maps Platform. An admin plans multi-stop fleet routes on a map (an ADK agent does the planning), a driver PWA simulates driving them navigator-style, and the backend raises deviation alerts and auto-reroutes. See README.md for the feature list and demo script.

## Commands

```bash
python3.11 -m venv venv && venv/bin/pip install -r requirements.txt   # once
cp .env.example .env                                                   # fill in keys
./run.sh                          # serve at http://localhost:8000 (admin UI at /)
rm fleet.db*                      # reset all demo data (trips, position log)
```

Tests (added with the pickup & delivery feature): `venv/bin/python tests/test_pickup_delivery.py` — deterministic routing/progress checks, no keys (uses `FAKE_ROUTES`). `eval/` holds ADK `AgentEvaluator` eval sets for the LLM agents (`eval/run.py`, needs a Gemini key — see `eval/README.md`). No linter or frontend build step. Broader verification is by exercising the running app: `curl` against the API and Playwright driving the real pages headless (import from a sibling project, e.g. `/hms/apps/test-automation/node_modules/playwright/index.mjs`; `google-chrome --headless=new --screenshot` for single shots). Restart the server after backend edits — `run.sh` does not auto-reload.

## Environment / keys

All config is env vars loaded from `.env` (see `.env.example`). Two Google keys: `GOOGLE_API_KEY` (Gemini, for the ADK agent) and `MAPS_API_KEY` (Maps JS + Routes API v2 + Places API New). Key quirks that shape the code:

- On an unbilled Maps key, Routes v2 and Places API (New) work but **legacy** Geocoding/Places do not — which is why place search/reverse-naming go through backend proxies (`/api/geocode`, `/api/revgeocode`) hitting Places New, and why toll estimates stay empty until a billed key is used.
- `FAKE_ROUTES=1` swaps the Routes API for straight-line routes so the entire pipeline (agent, simulator, deviation, reroute, SSE) works with no usable Maps key.

## Architecture

Single FastAPI app (`app/main.py`) serves the REST API, SSE streams, and the static frontend (same origin, no CORS, no auth). Storage is SQLite (`app/db.py`: trip JSON blobs + a per-tick position log) with runtime-only state (deviation counters, reroute guards, SSE queues) held in memory in `app/store.py`.

**Route planning is agent-mediated; rerouting is not.** `app/routing.py` owns the actual Routes API v2 call (field mask, waypoint optimization, traffic/toll extras, FAKE_ROUTES fallback) and returns the canonical route dict (`orderedStops/polyline/path/legs/steps/traffic/tollPrice/totals`). Two callers:

- Planning: `app/planner/service.py` runs the ADK `Agent` via `AgentRun` (`app/agent_runtime.py` — the shared `Runner` + `InMemorySessionService` wrapper both agents use; fresh session per request, plain `await`, never `asyncio.run()` in handlers). The agent calls the `compute_routes` tool (`planner/tools.py`), which wraps `routing.compute_route`. Prefer ADK components over hand-rolled equivalents: both agents use `PlanReActPlanner` (reason before acting), `output_schema` (Pydantic structured output) + `output_key`, and expose `root_agent` for `adk run`/`web`/`eval`.
- Auto-reroute (`_do_reroute` in `main.py`): calls `routing.compute_route` directly with `optimize=False` — deterministic, no LLM in the loop.

**Trusted data never round-trips through the LLM.** The tool stashes the full route in `tool_context.state["routes_api_raw"]` and returns only a small summary dict to the model (no polylines — token waste). The service reads geometry from session state and takes only the validated `output_schema` result (stop order + briefing) from the model; a bad generation can break the briefing, never the map. Deterministic inputs like avoid-tolls flow through session `state=` at `create_session`, not through the prompt.

**Deviation detection** (`app/deviation.py`) is rule-based: point-to-polyline distance with a threshold + consecutive-tick debounce. Matching is **windowed around the vehicle's known progress** (`runtime["along"]`, frozen while off-route, ahead-window bounded by physically plausible movement per tick). Do not "simplify" this back to min-distance-over-the-whole-polyline: routes that loop or double back (constant in Colombo) pass within meters of an off-route vehicle and mask real deviations.

**Reroute protocol**: a confirmed deviation kicks off a background task that recomputes from the current position through the remaining stops (found via leg-distance boundaries vs `along`), bumps `trip["routeVersion"]`, and broadcasts. The driver doesn't hold an SSE connection — it notices the version bump in its next `POST /position` response and refetches the trip mid-drive.

**Live updates are SSE, not WebSockets.** `store.broadcast(trip_id, event, data)` fans out to per-trip subscribers (`/api/trips/{id}/stream`) and a global stream (`/api/stream`, used by the admin fleet dashboard); every event carries `tripId`.

## Frontend

Plain HTML/JS in `static/`, no build. `admin.html`/`admin.js` is the dispatch console (Plan/Fleet tabs, global SSE, all vehicles on one map); `driver.html`/`driver.js` is the navigator-style PWA whose "driving" is a client-side simulator interpolating along the decoded polyline (the Deviate button applies a growing perpendicular offset). Shared helpers live in `static/js/common.js` (API fetch, polyline decode, markers, traffic overlays, theming) and `maps-loader.js` (fetches the key from `/api/config`, official bootstrap loader).

Conventions: light theme is default with dark as a toggle — all colors are CSS custom properties on `:root` overridden under `[data-theme="dark"]`, and map style/route colors follow via `themeAwareMap`/`mapThemeStyles()`. The driver map uses `mapId: "DEMO_MAP_ID"` (vector: tilt/heading camera + AdvancedMarker, falls back gracefully); the admin map uses a classic styled raster map, so `styles:` works there but not on the driver map. Bump the `CACHE` version in `static/sw.js` when changing driver-page shell files, or the PWA serves stale ones.

Design system: a modern minimalist layer, plus `static/css/tracking.css` (loaded after `modern.css`) for the tracking-style cards: parcel and run cards (`.pcard`, `.tcard`: id + status pill, `progressLine()` with a truck, from/to, customer or driver with call/email buttons), predefined-route cards (`.rcard`), detail-panel header bars, key-value insights and the ring timeline.

 `static/css/modern.css` (loaded last) re-tokens the light theme — purple `#6D35B3` (hover `#572A94`) only for primary buttons, active nav and interactive accents; page `#F8F9FC`, cards white, text `#172033`, muted `#667085`, border `#E8EAF0`, success `#168464`, error `#D92D20`, warning `#D97706` (warning text uses `--warning-ink` for contrast) — and the dark theme keeps its own tokens from `admin.html`. Light-theme tokens in `modern.css` live under `:root:not([data-theme="dark"])` so they never override the dark block. Base token blocks are in the `<style>` of `admin.html`, the shell in `static/css/console.css`, and `modern.css` wins last. Inter, 8px spacing, 12px cards / 8px controls. Layout: `#app` grid = 56px white top bar / "Operations overview" heading + 5 KPI cards (`#hero-main`) / sidebar / `#stage`. The sidebar is collapsible on desktop (`#nav-collapse`, remembered in localStorage `fleetops-nav`, class `body.nav-collapsed`), an icon rail on tablets and a slide-in drawer on phones (`#nav-burger`, `body.nav-open`, `setupNav()` in `palette.js`). The dashboard stage is a map card (`#dash-bar` is its header: Live / date / slider / time; `#map-wrap` its body) with the attention panel (`#dock-empty`) beside it, stacked under the map on tablet/phone; the rides table turns into cards on phones. Attention rows are `.dock-item` (severity dot + text tag, parcel reference, summary, chevron) rendered by `renderDock()`; the Late KPI card gets `.kpi-alert` only when something is late. Loading skeletons are plain markup replaced by the first render; `prefers-reduced-motion` is honoured. Menus (`.pop`) carry their own `--pop-*` colours; `setupMenus()` in `palette.js` wires them, `setTheme()` is in `common.js`. The light map style is `MAP_LIGHT_STYLE` in `common.js` (admin raster map only). Fleet markers are scaled by `FLEET_MARKER_SCALE`. Static files are served with `Cache-Control: no-cache` (`RevalidatingStatic`). `body[data-page]` (dashboard | parcels | fleet | attention | warehouse | registry | impact | reports; Impact and Reports are full pages in the side menu, `startImpact()` / `startReports()` run when shown) switches the stage grid via CSS; `switchTab()` is the only page switcher. The map (`#map-wrap`) and the floating cards (`#parcel-detail`, `#trip-detail`, `#dispatch-card`, `#run-picker`) are direct children of `#stage`. Extra information goes in accordions (`.acc` + `.acc-head`, `accHtml()`). The "rides at a time" board is `static/js/dashboard.js` over `GET /api/rides?at=` (`app/rides.py`). `palette.js` is the Ctrl/Cmd+K palette, shortcuts and compact-view toggle; research behind these choices is in `docs/ui-research.md`. Sentence case, no all-caps labels, no emoji — icons come from `ICONS`/`iconSvg()`.

## Dispatcher features (added on the Delivery-Management branch)

- `app/delivery.py` owns parcels/vehicles/drivers: eligibility (`check_eligibility`: count, size, dimensions, weight, volume, then driver availability/limits), parcel history (`add_event`, centralised in `set_parcel_status`), proof of delivery (images in the `pods` table, never in the parcel JSON) and failed attempts: a failure parks the shipment in `failed` with `review.state="pending"` — nothing is auto-returned or auto-requeued; `review_failed` (`POST /api/parcels/{id}/review`) reschedules it (a later day sets `holdUntil`, honoured by `is_plannable`) or returns it. Use `is_plannable`, not `PARCEL_PLANNABLE_STATUSES`, to decide what can go on a run.
- Pickup requests are parcels with `requestType: "pickup"` (customer address in `pickup`, `pickup.earliest` = customer cut-off, `pickup.latest` = collect-by = `deadline`, destination = the hub). `build_run_stops` emits a pickup stop plus a `hubReturn` drop that `routing.hub_last` forces to the end of every ordering; `has_special_handling` routes them through the deterministic sequencer (a pickup before its cut-off waits unless `earlyOk`). They are never auto-collected in `_check_stop_progress` — the driver posts `POST /api/parcels/{id}/collect` (in `DRIVER_ROUTES`); lateness is judged at collection, the hub drop is a receipt (`delivered`). `app/fit.py` (`GET /api/parcels/{id}/fit`) ranks runs for a pending parcel; adding goes through `POST /api/runs/{id}/parcels` (live re-plan). There is deliberately no domestic/international split — everything is one optimisation pool.
- `app/impact.py` (`GET /api/impact`, fuel settings `PUT /api/settings/fuel`) is the business-case report: baseline (stops in entry order, hub drops last) vs the planned order, both on a haversine x 1.3 yardstick, so savings never mix two measurement methods; fuel = km x L/100 km by vehicle type; plan-vs-actual and ETA accuracy use real data. Planned ETAs add `delivery.SERVICE_SECONDS` per stop and are re-computed from `startedAt` in `start_trip`. `replan.breakdown` (`POST /api/runs/{id}/breakdown`, preview unless `apply`) redistributes a broken run via `fit.suggest(exclude=...)`.
- `app/route_templates.py` (`/api/route-templates`, table `route_templates`) are predefined routes: code, name, zone (centre + radius), default driver, service days, start time and recurring pickups. `run_today` creates today's recurring pickup requests once per day (`templateId/templateStopId/templateDay` on the parcel), gathers pending parcels inside the zone and plans them deterministically via `create_run(..., deterministic=True)`; trips carry `templateCode/templateName`. Editing templates is supervisor-only, running one is dispatcher (`required_role`). UI: `static/js/routes.js` on the Runs page.
- `app/warehouse.py` (`/api/warehouse/loading`, `/receiving`, `POST /api/parcels/{id}/loaded`, `/api/runs/{id}/loaded`, `/api/parcels/{id}/received`): the loading bay lists, for each planned run, the parcels to hand to the driver in loading order (last stop first; pickups are not loaded at the hub) with `loadedAt/loadedBy`; the receiving desk lists collected pickups, undelivered parcels and returns awaiting `receivedAt`. Any status change clears `receivedAt`, and leaving `assigned`/`in_transit` clears `loadedAt`. UI: `static/js/warehouse.js`. The map is shown only where needed: list pages hide `#map-wrap` unless `body.pf-open` / `body.map-needed` (`showMapFor()`).
- Signatures are not captured in this app: PODs keep a `reference` to the separate e-signature process.
- `app/dispatcher/rules.py` is the deterministic, key-free "Suggest runs" (sweep + largest vehicle first, express first, skips drivers on leave/off shift). The Gemini agent is still available as `engine: "ai"`.
- Runs with express/priority parcels or windows bypass the AI planner: `routing.sequence_stops` + `delivery.plan_with_priorities`. `app/replan.py` edits existing runs (add/remove/move/reassign) via `routing.compute_route`; a live run re-plans from `trip["lastPosition"]` and bumps `routeVersion`.
- `app/notify.py` records customer messages and posts to `NOTIFY_WEBHOOK_URL` if set; public tracking is `GET /api/track/{no}` (rate limited, no PII beyond what the customer should see).
- `app/auth.py`: opt-in (`AUTH_ENABLED=1`) cookie sessions. Roles (admin, supervisor, dispatcher, support, warehouse, fleet, analyst, viewer) are permission sets (`ROLE_PERMS`, `ROLE_INFO` = pages + landing), enforced in one middleware via `required_perm(method, path)`; add a permission there when you add an endpoint. `/api/auth/me` returns the permissions/pages and `/api/auth/roles` lists every role. The client turns permissions into `body.can-*` classes (`applyRole()` in `users.js`, `can()` in scripts; CSS hides what a role can't use, in `tracking.css`). Driver endpoints (`DRIVER_ROUTES`) accept the driver's `k` key instead of a session — keep new driver-app endpoints in that list. Never return `token` fields to roles below dispatcher.
- `app/reports.py`: reporting + CSV (cells starting `= + - @` are neutralised).
- Tests are plain scripts, no keys: `tests/test_{pickup_delivery,pickup_requests,roles,route_templates,impact,capacity_dispatch,pod_failures,priority_shifts,replan,tracking_notify,reports,rides,auth}.py`. Each sets its own temp `DB_PATH`.

## Real-world operations (from the Sri Lanka courier research; `docs/real-world.md`)

- `app/cod.py`: cash on delivery. A parcel's `cod` is `{amount, state: due|collected|deposited|remitted, ...}` with `merchant` on the parcel. `POST /api/parcels/{id}/pod` refuses a COD parcel without `codCollected` (and `_check_stop_progress` never auto-delivers one). `ledger()` groups cash by rider (limit and hand-in hours from the `cod` setting), merchant and deposit; `deposit()` settles everything a rider holds and records the variance; `remit()` pays a merchant out. `until=` only exists so the seed can back-date. Endpoints `/api/cod/*` (`cod.read|write|remit`); the page is `static/js/field.js` (`startCash`).
- `app/risk.py`: `assess()` is an explainable score (reasons with points, never a black box); `customer_index()` derives phone-number history and the last successful drop-off position from parcels, so there is no separate address table; `queue()` is the confirmation call list; `respond()` is the receiver's answer (confirm / reschedule sets `holdUntil` / cancel), shared by `POST /api/parcels/{id}/confirmation` (staff) and the public, rate-limited `POST /api/track/{no}/respond`; `first_attempt()` feeds Reports. `/api/track` returns `canRespond`, `confirmation`, `cashDue`, `landmark` for `static/track.html`.
- `app/disruptions.py`: `blocking(parcel)` is checked inside `delivery.is_plannable`, so every planner honours area holds; creating one removes planned (not started) parcels from their runs and sends a `delayed` message; live runs are only reported. `mark_absent` frees planned runs. `forecast()` and `fuel_quota()` are estimates (stops/day by vehicle type; litres from the Impact fuel settings), labelled as such in the UI.
- Permissions `cod.read|write|remit` (warehouse counts cash, supervisor pays out); `cash` is a page. UI lives in `static/js/field.js` (Cash page, Attention extras, parcel risk panel, Reports first-attempt) with styles at the end of `tracking.css`. Tests: `tests/test_realworld.py`.

## Routes API gotchas (learned the hard way)

- The `X-Goog-FieldMask` header is mandatory; omitting it is a 400.
- `optimizeWaypointOrder` needs ≥2 intermediates and is incompatible with `TRAFFIC_AWARE_OPTIMAL` (plain `TRAFFIC_AWARE` is fine).
- Durations arrive as strings like `"3600s"`; route-level `speedReadingIntervals` indices map directly onto the overview polyline points.
- The router optimizes **time, not distance** — a 25 km expressway loop legitimately beats a 13 km urban crawl. If a route "looks wrong", compare alternatives before assuming a bug (`avoidTolls` usually flips it).
